# Schema tooling

How the editor's document model is captured, checked and shipped. This is tooling for people working
**on** the repo — the editor's own docs live in `apps/site/src/content/docs`.

## What the schema is, and is not

It is the **roundtrip format**: the editor's own ProseMirror document model. It is not QTI, and
passing these checks does not mean a document is valid QTI.

That distinction is deliberate and worth holding on to. The plan is for an LLM to generate the
roundtrip format — one interaction for a fragment in the editor, or several plus prose — and be
validated against this contract. Converting to QTI, carrying `score` and `correct-response`, is a
later and separate step. So read every rule below as *"is this a legal editor document"*, never
*"is this legal QTI"*.

Where a rule is narrower than the standard, a `XSD:` note records what QTI would have permitted.
Those are explanations, not conformance claims.

## The pipeline

`schema/` reads **authored → compute → write**:

| file | role |
| --- | --- |
| `notes.ts` | Hand-authored. 21 prose notes keyed by node name, plus `IDENTIFIED`. What a human knows and the schema cannot. |
| `content-model.ts` | Builds the real composed schema and shapes it. Pure — no I/O, so a test can import it without writing files. |
| `generate.ts` | The CLI. Writes `content-model.json` and the per-interaction fixtures. |
| `content-model.json` | Output, and the published artifact. |
| `__interactions__/*.json` | Output. One file per interaction, for readable diffs. |

The compute/write split is not decoration. An earlier version built *and* wrote at module top level,
so importing it wrote files as a side effect — which forced the checker to shell out to a subprocess
just to compare against a fresh run. Separating them deleted that subprocess.

**The composed schema is the source of truth; the JSON is a projection of it.** Interactions declare
their own node specs next to their parse rules and commands, and the composer unions them — which is
what lets a host build an editor with a subset of interactions. The JSON exists because consumers
outside this repo cannot compose anything.

## Regenerating

```bash
just schema        # regenerate, then verify
just schema-check  # verify only
```

**Read the diff before committing it.** A changed fixture is a changed editor contract, and
`content-model.json` is consumed outside this repo. Regeneration is deterministic — same schema in,
byte-identical file out — so a dirty diff always means something really moved.

## The two gates

Both run in `pnpm test`, in CI, and in the staged-only pre-commit hook.

**`schema/content-model.browser.test.ts`** — *did the grammar change?* Per-interaction fixtures (a
failure names the interaction), a whole-model comparison, coverage in both directions, notes
validity, and a proof that `content-model.json` rebuilds into a working ProseMirror schema on its
own.

The whole-model assertion compares **strings, not deep equality**, because node order is
load-bearing: ProseMirror resolves a content expression's default type by first match. Nothing sorts
`nodes` — a reordering is real drift, and a deep-equal assertion would wave it through.

**`schema/markup-contract.browser.test.ts`** — *is this shape legal?* The same contract stated one
example at a time, which is the form a human can check by eye. Every `XSD:` narrowing has a matching
rejection case, so a note and the behaviour it describes cannot drift apart.

## `schemaVersion`

`content-model.json` carries a fingerprint of the grammar, for example:

```json
"schemaVersion": "fnv1a64-f04508231bf07b42"
```

It is **derived, never hand-bumped** — a number someone has to remember to increment is wrong
exactly when it matters. It covers everything a document's validity depends on: `topNode`, each
node's content expression, group, marks, flags, attribute defaults, `tagName`, `placeholder`, the
marks, the group index and `identified`.

**Notes are excluded.** Rewording why a prompt is narrowed changes nothing a document's validity
depends on, so it must not invalidate a consumer's cached schema or read as a breaking change. Both
halves of that are asserted: the version does not move when a note changes, and does move when a
content expression does.

## Consuming it

```js
import contentModel from '@citolab/prose-qti/content-model';
```

`packages/prose-qti` copies the generated file into its `dist` at build time. There is no second
committed copy, so the two cannot drift; if the source file ever went missing the build fails
loudly, which is better than silently shipping a stale document model.

Each node carries its `note` in the JSON, so a consumer reading only this file gets the reasoning as
well as the grammar — *"the XSD makes `qti-prompt` optional; the editor requires it"* is exactly what
a generator needs and cannot infer from `content: "qtiPromptParagraph"` alone.

For non-npm consumers — the C# and Python parsers this format is aimed at — attach
`content-model.json` to a GitHub release rather than expecting them to install a package.
